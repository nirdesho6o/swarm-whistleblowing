- **Pre-registered results (`phase15_results.md`): every count, rate, seed count and verdict reproduces
  exactly.** The intervals differ only by bootstrap noise (≤ 0.4 pts), and one per-seed value differs by 0.1
  through rounding. No bugs found.
- **Exploratory §1, §2: reproduce exactly.**

  "bare/non-numeric" entries are `=!01` on P09, whose true answer is 1. By the file's own definition ("parses as
  an integer equal to the true answer") they are correct-number entries. The cause is Python's `int("01", 0)`,
  which rejects a leading zero. The headline claims and some interpretive text change; details below.
- §3 (difficulty) and §4 (recomputation heuristic) were not part of this check and were not verified.

### §5 `=!` content classes: **classification bug**

- **What matches:** using the same parse as the original (`int(x, 0)`, which my pre-written rule also used),
  every count and verdict mix reproduces exactly:
  - phase totals: v1.0 282/103/44, v1.1 853/468/189, v1.2 203/58/67;
  - `=!0` counts: 68/363/30;
  - every per-model and all-phase row: for example all-phase correct 885/3687, wrong 998/1169, bare
    117/492.
- **The problem:** `int("01", 0)` raises `ValueError` (Python forbids leading zeros in base-0 literals).
  - Every entry in the "bare/non-numeric" class, in every phase and model, is the string `=!01`.
  - `=!01` occurs only on **P09 ("last two digits of 7^100"), true answer 1**, so these entries carry the
    correct answer.
  - The file's own definition says correct number = "parses as an integer equal to the true answer". The
    bare/non-numeric class should be **empty**.
- **Likely cause:** a bug, the same pitfall my own pre-written rule hit.
